# 📦 BaanDee Stockout Risk & Restock Manager
**ระบบต้นแบบสำหรับการคัดกรองข้อมูล ประเมินความเสี่ยงสินค้าขาดสต็อก และบริหารใบสั่งซื้ออัตโนมัติ (Data Product Prototype)**

---

## 🎯 1. ปัญหา ผู้ใช้ และคุณค่าที่คาดหวัง (Problem, Users & Expected Value)

1. **ผู้ใช้หลักคือใคร (Target Users):**
   -  ⁠เจ้าหน้าที่บริหารคลังสินค้า (Warehouse Staff) และผู้จัดการฝ่ายจัดซื้อ
2. **ผู้ใช้กำลังพยายามทำงานอะไร (User's Job-to-be-Done):**
   - ตรวจสอบปริมาณสินค้าคงเหลือในคลังแบบเรียลไทม์ผ่านระบบ เพื่อเช็กว่าสินค้าตัวใดมีจำนวนคงเหลือเป็นศูนย์ (available_qty = 0) หรือต่ำกว่าเกณฑ์ความปลอดภัย รวมถึงวิเคราะห์จุดขาดแคลน (Stock Gap) และวางแผนรอบการสั่งซื้อสินค้าล่วงหน้าจากซัพพลายเออร์ให้สอดคล้องกับความต้องการจริง[span_0](start_span)[span_0](end_span)'
3. **ปัญหาในกระบวนการปัจจุบันคืออะไร (Current Pain Points):**
   - ⁠ข้อมูลสต็อกสินค้าและรายละเอียดสินค้ากระจัดกระจายอยู่คนละไฟล์ ขาดการเชื่อมโยง ทำให้เจ้าหน้าที่ต้องเสียเวลาตรวจสอบและคำนวณด้วยมือ (Manual Check) เสี่ยงต่อความผิดพลาด ไม่มีระบบแจ้งเตือนอัตโนมัติเมื่อสินค้าใกล้หมด ส่งผลให้ผู้จัดการฝ่ายจัดซื้อสั่งซื้อสินค้าล่าช้า เกิดปัญหา "สินค้าขาดมือ" (Stockout) สูญเสียโอกาสในการขายสินค้าในหมวดหมู่สำคัญ (เช่น Kitchen, Bathroom)⁠
4. **ต้นแบบจะช่วยให้กระบวนการดีขึ้นอย่างไร (Value Proposition):**
   - ⁠บูรณาการและเชื่อมโยงข้อมูลคลังสินค้าเข้ากับข้อมูลรายละเอียดสินค้า (ใช้ product_id เป็นคีย์เชื่อมโยง)[span_1](start_span)[span_1](end_span) มีหน้าจอแดชบอร์ดที่ช่วยคัดกรอง วิเคราะห์ และแสดงผลจุดที่สินค้าขาดแคลน (Stock Gap) ได้อย่างชัดเจน รวดเร็ว ช่วยลดขั้นตอนการทำงานที่ซ้ำซ้อน และอนุญาตให้ผู้ใช้สามารถกดบันทึกหรืออัปเดตข้อมูลจำนวนสต็อกผ่านหน้าจอได้จริงโดยข้อมูลจะถูกบันทึกคงอยู่บนระบบ[span_2](start_span)[span_2](end_span)⁠
5. **ผลลัพธ์ใดเป็นเพียงสมมติฐานที่ยังต้องทดลองกับผู้ใช้จริง (Assumptions to Validate):**
   - การกำหนดเกณฑ์จุดสั่งซื้อ (Reorder Point) และค่าความปลอดภัยของสต็อก (Safety Stock) ที่คำนวณจากข้อมูลจำลอง (Synthetic Data)[span_3](start_span)[span_3](end_span) ว่าเพียงพอต่อความต้องการจริงหรือไม่ โดยยังต้องนำต้นแบบไปให้เจ้าหน้าที่คลังและผู้จัดการฝ่ายจัดซื้อทดลองใช้งานหน้างานจริง เพื่อเก็บฟีดแบ็กและปรับแก้เกณฑ์การแจ้งเตือนให้สอดคล้องกับพฤติกรรมการซื้อและการส่งออกที่แท้จริงต่อไป⁠

## 🗺️ 2. แผนภาพข้อมูล ความสัมพันธ์ และคุณภาพข้อมูล (Data Map & Data Quality)

### 2.1 แหล่งข้อมูลที่ใช้ในโครงงาน (Data Sources)
โครงงานนี้นำข้อมูลมาเชื่อมกันจาก 2 กลุ่มแหล่งข้อมูล (รวม 3 ตารางต้นทาง) โดย **ไม่แก้ไขทับข้อมูลต้นฉบับ**:

1. **ข้อมูลต้นฉบับจากชุด BaanDee (`data/raw/`):**
   - **`Raw_Stock.csv`**: เก็บข้อมูลจำนวนสินค้าคงคลังปัจจุบัน (`sku_id`, `warehouse_id`, `available_qty`, `as_of`)
   - **`Products.csv`**: เก็บข้อมูลรายละเอียดสินค้า (`sku_id`, `product_name`, `category`, `unit_price`)
2. **ข้อมูลแหล่งใหม่ที่ทีมออกแบบและสร้างเพิ่ม (`data/generated/`):**
   - **`Supplier_SLA.csv`**: ตารางข้อมูลข้อตกลงระดับการให้บริการของผู้จัดจำหน่ายและอัตราการระบายสินค้า (`sku_ref`, `supplier_name`, `daily_burn_rate`, `lead_time_days`, `contract_date`, `contact_no`)
   - **วิธีการสร้างและสมมติฐาน:** สร้างข้อมูลสังเคราะห์ (Synthetic Data) เพื่อจำลองพารามิเตอร์ด้าน Supply Chain ที่ไม่มีในชุดข้อมูลเดิม โดยตั้งสมมติฐานว่าสินค้าแต่ละรายการมีอัตราการขายเฉลี่ยต่อวัน (`daily_burn_rate`) และระยะเวลาจัดส่งของซัพพลายเออร์ (`lead_time_days`) ที่แตกต่างกัน พร้อมทั้งจำลองข้อมูลที่บกพร่อง (Dirty Data) เข้าไปเพื่อทดสอบระบบคัดกรองข้อมูล

### 2.2 แผนภาพความสัมพันธ์และกฎการเชื่อมข้อมูล (Data Map & Join Rules)

```text
+-------------------+       +-------------------+       +-----------------------+
|     Raw_Stock     |       |     Products      |       |     Supplier_SLA      |
| (data/raw/)       |       | (data/raw/)       |       | (data/generated/)     |
+-------------------+       +-------------------+       +-----------------------+
| PK: sku_id        |<----->| PK: sku_id        |<----->| FK: sku_ref           |
| available_qty     |       | product_name      |       | supplier_name         |
| as_of             |       | category          |       | daily_burn_rate       |
+-------------------+       | unit_price        |       | lead_time_days        |
                            +-------------------+       | contract_date         |
                                                        | contact_no            |
                                                        +-----------------------+
                                      |
                    [ Join Key: Normalized SKU_ID ]
                    Rule: String(id).trim().toUpperCase()
                                      |
                                      v
                       +-----------------------------+
                       | Data Validation & Cleaning  |
                       +-----------------------------+
                              /               \
               (ผ่านเกณฑ์ทั้งหมด)                 (พบความผิดปกติ/กำกวม)
                            /                   \
                           v                     v
             +-----------------------+ +-----------------------+
             |     Cleaned_Data      | |      Quarantine       |
             | (data/cleaned/)       | | (data/cleaned/)       |
             | พร้อมคำนวณความเสี่ยง     | | แยกไว้ให้มนุษย์ตรวจสอบ   |
             +-----------------------+ +-----------------------+
```

- **กฎการเชื่อมข้อมูล (Join Key & Normalization Rule):** ใช้รหัสสินค้า (`sku_id` และ `sku_ref`) เป็น Primary/Foreign Key ในการเชื่อมทั้ง 3 ตารางเข้าด้วยกัน โดยใช้กฎ `String(sku).trim().toUpperCase()` เพื่อตัดช่องว่างและปรับเป็นตัวพิมพ์ใหญ่ทั้งหมดก่อนทำการจับคู่

### 2.3 ปัญหาคุณภาพข้อมูล หลักฐาน และการจัดการ (Data Quality Issues & Correction Rules)
ระบบไม่เดาหรือแก้ไขข้อมูลที่กำกวมเองโดยไม่มีหลักฐาน แต่ใช้การแยกข้อมูลออกเป็นตาราง `Cleaned_Data` และ `Quarantine` ดังนี้:

| ลำดับ | ปัญหาคุณภาพข้อมูลที่พบ | หลักฐานในข้อมูลดิบ (ตัวอย่าง) | วิธีตรวจพบ (Detection Rule) | วิธีจัดการ (Correction / Quarantine Rule) | ผลลัพธ์ก่อน - หลังการจัดการ |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1** | **รูปแบบ Key ไม่เป็นมาตรฐาน (Inconsistent Key Formatting)** | ใน `Supplier_SLA` พบรหัส `sku-0011` (ตัวพิมพ์เล็ก) ในขณะที่ตาราง `Products` ใช้ `SKU-0011` | ตรวจสอบด้วย String Matching หากเปรียบเทียบตรงๆ จะทำให้ Join ข้อมูลไม่ติด | ใช้กฎ Normalization แปลงรหัสสินค้าด้วย `.trim().toUpperCase()` ก่อนนำมาเชื่อมตาราง | **ก่อน:** เชื่อมข้อมูล `sku-0011` ไม่สำเร็จ<br>**หลัง:** จับคู่กับ `SKU-0011` ได้ถูกต้อง |
| **2** | **ค่าตัวเลขทางธุรกิจเป็นไปไม่ได้ (Invalid Business Metrics)** | พบ `daily_burn_rate` หรือ `lead_time_days` มีค่าติดลบหรือเท่ากับ $0$ (เช่น อัตราการขาย $\le 0$ หรือเวลาส่งของ $< 0$) | เงื่อนไข `isNaN(burnRate) \|\| burnRate <= 0 \|\| isNaN(leadTime) \|\| leadTime < 0` | **ไม่เดาค่าทดแทน** ระบบคัดแยกรายการไปไว้ที่แท็บ `Quarantine` พร้อมระบุสาเหตุชัดเจน | **ก่อน:** คำนวณวันคงเหลือผิดพลาด (หารด้วยศูนย์หรือได้ค่าติดลบ)<br>**หลัง:** ข้อมูลถูกบล็อกเข้า `Quarantine` ไม่นำไปแสดงให้ฝ่ายจัดซื้อสั่งของผิด |
| **3** | **ข้อมูลสำคัญสูญหายหรือวันที่กำกวม (Missing Contact / Ambiguous Date)** | ใน `Supplier_SLA` ของ `sku-0011` ไม่มีเบอร์ติดต่อ (`contact_no` ว่างเปล่า) หรือรูปแบบวันที่สัญญาไม่ชัดเจน | เงื่อนไขตรวจสอบค่าว่าง `contact === ""` หรือรูปแบบวันที่ไม่สามารถแปลงเป็นมาตรฐานได้ | แยกรายการเข้าแท็บ `Quarantine` เพื่อให้เจ้าหน้าที่ข้อมูล (Human-in-the-loop) ติดตามแก้ไขกับซัพพลายเออร์ | **ก่อน:** พนักงานอาจออกใบสั่งซื้อให้ซัพพลายเออร์ที่ติดต่อไม่ได้<br>**หลัง:** ระบบระงับการสั่งซื้อซัพพลายเออร์รายนี้จนกว่าข้อมูลจะได้รับการแก้ไข |

## 🏗️ 3. สถาปัตยกรรม เหตุผลในการเลือกเครื่องมือ และขอบเขตระบบ (Architecture & System Boundary)

### 3.1 เหตุผลในการเลือกเครื่องมือ (Tool Selection)
ทีมเลือกพัฒนาต้นแบบด้วย **Google Sheets ร่วมกับ Google Apps Script (JavaScript & HTML Service)** เนื่องจาก:
- **ความเหมาะสมกับโจทย์:** พนักงานคลังสินค้าและจัดซื้อคุ้นเคยกับอินเทอร์เฟซแบบตาราง (Spreadsheet) อยู่แล้ว แต่ระบบช่วยยกระดับด้วย Custom Menus, Modal Dialogs และระบบอัตโนมัติ (Automation) ลดความผิดพลาดจากการพิมพ์เอง
- **Data Persistence ที่ตรวจสอบได้จริง:** ข้อมูลทุกขั้นตอน (Raw, Cleaned, Quarantine, Purchase Orders) ถูกแยกเก็บในแต่ละ Sheet อย่างชัดเจน สามารถตรวจสอบย้อนกลับได้ทันที

### 3.2 หน้าที่ของแต่ละส่วนและการคำนวณความเสี่ยง (Component Responsibilities & Risk Logic)
1. **Data Pipeline (`runDataPipeline`)**: ดึงข้อมูลจาก `Raw_Stock`, `Products`, และ `Supplier_SLA` มาคัดกรองแยกเข้า `Cleaned_Data` และ `Quarantine` พร้อมคำนวณระยะเวลาที่สต็อกจะหมด ($\text{Days Left}$):
   $$\text{Days Left} = \frac{\text{Available Qty}}{\text{Daily Burn Rate}}$$
2. **Risk Assessment Logic (การประเมินความเสี่ยงพร้อมอุดช่องโหว่ Demand Spike & Delay):**
   กำหนดค่ากันชน $\text{Safety Stock} = 2\text{ วัน}$ และเกณฑ์ขั้นต่ำ $\text{Min Qty Threshold} = 2\text{ ชิ้น}$
   - 🔥 **CRITICAL (เสี่ยงของขาด ต้องสั่งด่วน!):** เมื่อ $\text{Days Left} \le \text{Lead Time}$ หรือ $\text{Available Qty} \le 2$
   - 🟡 **MEDIUM (ความเสี่ยงปานกลาง เตรียมสั่งซื้อ):** เมื่อ $\text{Lead Time} < \text{Days Left} \le (\text{Lead Time} + 2)$
   - ✅ **SAFE (ปลอดภัย):** เมื่อ $\text{Days Left} > (\text{Lead Time} + 2)$ และ $\text{Available Qty} > 2$
3. **Closed-loop PO & Goods Receipt (`processPurchaseOrder` & `processReceivePO`)**:
   - สร้างใบสั่งซื้อและบันทึกลงแท็บ `Purchase_Orders` (ป้องกันการสั่งสินค้าที่ติด `Quarantine`)
   - รับสินค้าเข้าคลังจากรหัส `PO_ID` โดยเปลี่ยนสถานะเป็น `Received` และบวกจำนวนสินค้าเพิ่มกลับเข้าไปใน `Raw_Stock` พร้อมอัปเดตเวลา `as_of` อัตโนมัติ (ป้องกันการกดรับของซ้ำ)

### 3.3 ขอบเขตระหว่างระบบ (API Boundary & Hybrid Web Portal)
ระบบมีจุดเชื่อมต่อข้ามระบบผ่านฟังก์ชัน `doGet(e)` และ `simulateAPIRequest(sku)` ของ Google Apps Script Web App โดยทำงานแบบ Hybrid:
- **รูปแบบที่ 1: Web UI Portal (สำหรับผู้ใช้งานภายนอก/สาขาอื่น):** เมื่อเปิด Web App URL โดยไม่ระบุพารามิเตอร์ ระบบจะแสดงหน้าเว็บ HTML (`BaanDee Stock Portal`) ให้ค้นหาสถานะสินค้าแบบ Real-time
- **รูปแบบที่ 2: REST API Endpoint (สำหรับระบบภายนอกเชื่อมโยงข้อมูล):** เมื่อส่ง HTTP `GET` Request พร้อมพารามิเตอร์ `?sku={SKU_ID}` ระบบจะส่งข้อมูลกลับเป็น `application/json` โดยรองรับครบ 3 สถานการณ์:
  1. **ได้รับข้อมูลสำเร็จ (`status: "success"`):** คืนค่าข้อมูลสินค้า จำนวนคงเหลือ วันคงเหลือ และสถานะความเสี่ยง
  2. **ไม่พบข้อมูลหรือถูกกักกัน (`status: "not_found"`):** แจ้งเตือนเมื่อรหัสสินค้าไม่มีในระบบ หรือซัพพลายเออร์ติดสถานะ `Quarantine`
  3. **พารามิเตอร์ไม่ครบถ้วน/ข้อผิดพลาด (`status: "error"`):** แจ้งเตือนข้อกำหนดการใช้งาน API เมื่อไม่ได้ระบุรหัสสินค้า

### 3.4 เหตุผลในการใช้กฎทางธุรกิจแทน Generative AI ในตัวผลิตภัณฑ์ (Why Rule-based over Generative AI)
ตามข้อกำหนดข้อที่ 4 ของโจทย์ โครงงานนี้ตัดสินใจ **ไม่ใช้ Generative AI / LLM ในการคำนวณสต็อกหรือออกใบสั่งซื้อ** ด้วยเหตุผลทางวิศวกรรมข้อมูลดังนี้:
- **ความแม่นยำและตรวจสอบย้อนกลับได้ (Deterministic & Auditable):** การคำนวณจุดสั่งซื้อ ($\text{Days Left}$), การคำนวณมูลค่าใบสั่งซื้อ ($\text{Unit Price} \times \text{Order Qty}$) และการตรวจสอบเงื่อนไขซัพพลายเออร์ ต้องการความถูกต้องทางคณิตศาสตร์ $100\%$ การใช้กฎทางธุรกิจ (Rule-based Logic) ป้องกันความเสี่ยงเรื่อง AI Hallucination (การสร้างตัวเลข ราคา หรือวันที่ปลอม) ได้อย่างเด็ดขาด
- **ความเร็วและเสถียรภาพ (Zero Latency & Reliability):** กฎการคัดกรองทำงานได้ทันทีโดยไม่ต้องพึ่งพา API ของโมเดลภายนอก และไม่มีค่าใช้จ่ายแฝงในการประมวลผล

## 🚀 5. วิธีติดตั้งและเริ่มระบบทีละขั้น (Installation & Setup Guide)

### วิธีที่ 1: ทดสอบผ่านระบบต้นแบบที่ทีมติดตั้งไว้แล้ว (แนะนำสำหรับอาจารย์ผู้ตรวจ)
1. **เข้าใช้งาน Google Sheets (Internal System & GUI):**
   - เปิดลิงก์ Google Sheets ของโครงงาน (ตั้งค่าสิทธิ์เป็น Editor เพื่อให้ทดสอบการบันทึกข้อมูลได้)
   - บนแถบเมนูด้านบน เลือก **`🚀 ระบบจัดการสต็อก BaanDee`**
   - *หมายเหตุสำคัญสำหรับการกดครั้งแรก:* หากระบบ Google แจ้งเตือนการขอสิทธิ์ (Authorization Required) ให้กด **Advanced (ขั้นสูง)** $\rightarrow$ เลือก **Go to ... (unsafe)** $\rightarrow$ กด **Allow (อนุญาต)** เพื่อให้สคริปต์ทำงานได้
2. **เข้าใช้งาน Web Portal & REST API (External System Boundary):**
   - **หน้าเว็บค้นหาสต็อก (Web UI):** เปิดลิงก์ Web App URL บนเบราว์เซอร์เพื่อพิมพ์ค้นหารหัสสินค้า
   - **เรียกใช้งานผ่าน REST API (JSON):** เติมพารามิเตอร์ `?sku=SKU-0001` ต่อท้าย Web App URL

### วิธีที่ 2: การสร้างระบบซ้ำด้วยตนเองจาก Repository (Reproducibility Setup)
1. สร้างไฟล์ Google Sheets ใหม่ และสร้างแท็บจำนวน 6 แท็บโดยตั้งชื่อให้ตรงตามนี้:
   `Raw_Stock`, `Products`, `Supplier_SLA`, `Cleaned_Data`, `Quarantine`, `Purchase_Orders`
2. นำเข้าไฟล์ CSV จากโฟลเดอร์ `data/raw/` (`Raw_Stock.csv`, `Products.csv`) และ `data/generated/` (`Supplier_SLA.csv`) เข้าสู่แท็บที่ตรงกับชื่อไฟล์
3. ไปที่เมนู **ส่วนขยาย (Extensions) > Apps Script** ลบโค้ดเดิมออกทั้งหมด แล้วคัดลอกโค้ดจากไฟล์ `scripts/main_app_script.js` ไปวางและกด **บันทึก (Save)**
4. การเปิดใช้งาน API / Web App:
   - กดปุ่ม **Deploy (การทำให้ใช้งานได้) > New deployment (การทำให้ใช้งานได้รายการใหม่)**
   - เลือกประเภทเป็น **Web app (เว็บแอป)**
   - ตั้งค่า *Execute as* เป็น `Me` และ *Who has access* เป็น `Anyone` จากนั้นกด Deploy
5. รีเฟรชหน้า Google Sheets 1 ครั้ง เมนู **`🚀 ระบบจัดการสต็อก BaanDee`** จะปรากฏขึ้นพร้อมใช้งาน

*(ดูรายละเอียดการตั้งค่าตัวแปรสภาพแวดล้อมเพิ่มเติมได้ที่ไฟล์ `.env.example`)*

## 🎬 6. กรณีสาธิตหลักและผลลัพธ์ที่คาดหวัง (Main Demo Scenarios)

### กรณีที่ 1: การทำงานสำเร็จแบบครบวงจร (End-to-End Success Flow)
1. **คัดกรองและประเมินความเสี่ยง:** กดเมนู `1. รันระบบคัดกรองข้อมูล (Run Pipeline)` ระบบจะดึงข้อมูลที่ผ่านเกณฑ์เข้าสู่แท็บ `Cleaned_Data` พร้อมคำนวณ `Days Left` และจัดระดับความเสี่ยง (`CRITICAL`, `MEDIUM`, `SAFE`) รวมถึงแสดงเวลาอัปเดตข้อมูล
2. **ตรวจสอบหลักฐานและรายการสั่งด่วน:** กดเมนู `2. สรุปรายการต้องสั่งด่วน (Dashboard)` หน้าต่างสรุปจะแสดงเฉพาะสินค้าที่มีสถานะ `🔥 CRITICAL` เพื่อให้ผู้ตัดสินใจเห็นหลักฐานชัดเจน
3. **สร้างและบันทึกข้อมูลใหม่ (Create PO):** กดเมนู `3. ออกใบสั่งซื้อ (Create PO)` กรอกรหัส `SKU-0001` จำนวน `10` ชิ้น ระบบจะดึงราคาต่อหน่วยและชื่อซัพพลายเออร์มาคำนวณยอดรวม พร้อมสร้างรหัสใบสั่งซื้อใหม่บันทึกลงแท็บ `Purchase_Orders`
4. **แก้ไขข้อมูลและอัปเดตสต็อกอัตโนมัติ (Receive PO):** คัดลอกรหัส `PO_ID` ที่เพิ่งสร้าง ไปกดเมนู `4. รับสินค้าเข้าคลัง (Receive PO)` ระบบจะเปลี่ยนสถานะใน `Purchase_Orders` เป็น `Received (รับเข้าคลังแล้ว)` และบวกจำนวนสินค้าเพิ่มในแท็บ `Raw_Stock` อีก $10$ ชิ้น พร้อมอัปเดตเวลา `as_of` ทันที

### กรณีที่ 2: กรณีที่ระบบต้องหยุด ระงับการทำงาน และส่งต่อให้มนุษย์ (Failure & Human Review Flow)
1. **การกักกันข้อมูลที่มีปัญหา (Quarantine):** เมื่อรัน Pipeline รายการที่มีปัญหาคุณภาพข้อมูล (เช่น `SKU-0003`, `SKU-0004`, `sku-0011`) จะไม่ถูกนำมาคำนวณความเสี่ยง แต่ถูกแยกไปเก็บในแท็บ `Quarantine` พร้อมระบุสาเหตุเพื่อให้เจ้าหน้าที่ข้อมูลตรวจสอบ
2. **การบล็อกการสั่งซื้อสินค้าที่ไม่ปลอดภัย (Blocked Order):** เมื่อผู้ใช้พยายามออกใบสั่งซื้อ (Create PO) สำหรับรหัส `SKU-0011` ซึ่งซัพพลายเออร์ไม่มีเบอร์ติดต่อและติดอยู่ใน `Quarantine` ระบบจะหยุดการทำงานและแจ้งเตือนข้อผิดพลาดทันที ไม่ยอมให้สร้างใบสั่งซื้อ
3. **การป้องกันการรับสินค้าซ้ำ (Duplicate Receipt Prevention):** หากนำรหัส `PO_ID` ที่รับเข้าคลังไปแล้วมากดรับซ้ำ ระบบจะตรวจสอบสถานะและบล็อกการบวกสต็อกซ้ำทันที

## ⚠️ 7. ข้อจำกัดและสิ่งที่ยังไม่ควรนำไปใช้จริง (Limitations & Risks)

1. **การรองรับผู้ใช้งานพร้อมกัน (Concurrency & Race Conditions):** เนื่องจากใช้ Google Sheets เป็นฐานข้อมูล หากมีพนักงานกดรับสินค้าหรือแก้ไขสต็อกพร้อมกันหลายสิบคนในเสี้ยววินาทีเดียวกัน อาจเกิดการเขียนทับข้อมูล (Overwriting) จึงยังไม่เหมาะกับคลังสินค้าระดับหลายหมื่นรายการที่มี Transaction ต่อวินาทีสูง
2. **สมมติฐานอัตราการขายคงที่ (Static Burn Rate Assumption):** ค่า `daily_burn_rate` ในต้นแบบนี้เป็นค่าเฉลี่ยคงที่ ยังไม่ได้ดึงยอดขายรายวันแบบไดนามิกตามฤดูกาล (Seasonality) หรือช่วงโปรโมชันใหญ่ (เช่น 10.10, 11.11)
3. **การควบคุมสิทธิ์ระดับแถว (Row-level Security):** ผู้ใช้ที่ได้รับสิทธิ์ Editor ใน Google Sheets เพื่อกดรันสคริปต์ ยังสามารถเข้าไปแก้ไขตัวเลขในตารางด้วยมือได้โดยตรง ในการใช้งานจริงระดับองค์กรควรแยกส่วน Database ออกจากส่วน Front-end อย่างเด็ดขาด
